## 1.Linux进程管理

> 进程是程序的一次运行实例。排查时先确认身份、父子关系和资源状态，再决定是否发送终止信号。

### 1.1 进程与父子关系

- **PID**：进程标识，由内核分配，退出后可被复用；不是固定值，也不能简单说成随机数。
- **PPID**：父进程标识。
- 常见启动路径是先通过 fork 等机制创建子进程，再由子进程执行 execve 替换程序映像；并非所有子进程都会执行新程序。
- fork 后父子进程通常使用写时复制，不是立即把父进程所有内存物理复制一份。
- **进程注入**：使代码在另一进程中执行的一类技术；不能只凭正常进程名判断其可信，也不能只凭名称异常就确认注入。

### 1.2 查看进程

以下 ps 说明以 Linux 上的 **procps-ng** 为主，BusyBox 等实现的选项和字段可能不同。

```bash
ps -l                    # 默认选择范围的长格式
ps -le                   # 所有进程，长格式
ps aux                   # BSD 风格，包含 CPU、内存等信息
ps -ef                   # 所有进程，完整格式
ps -ef | grep php        # 简单文本匹配，可能包含 grep 自身
ps -u sam                # 按有效用户选择
pgrep -a -u sam          # 显示匹配有效 UID 的 PID 和命令行
```

| 字段 | 含义 |
| --- | --- |
| F | 标志位之和：1 表示已 fork 未 exec；4 表示使用过超级用户权限；5 为二者之和，不表示“当前一定是 root” |
| S／STAT | 状态；R 为运行或就绪，S 为可中断睡眠，D 为不可中断睡眠，Z 为僵尸 |
| UID、PID、PPID | 用户身份、进程号、父进程号，UID 的具体口径按格式核对 |
| C、%CPU | CPU 使用统计，不等同于某一瞬间的采样占用 |
| PRI／PR、NI | 调度优先级显示和 nice 值；不同策略、格式的数值含义有差异 |
| ADDR | 传统地址字段，现代系统常不提供有效值 |
| SZ | 映像大小，按页计，不是常驻物理内存；RSS、VSZ 另有口径 |
| WCHAN | 睡眠等待所在的内核函数，显示缺失不能单独证明进程正在运行 |
| TTY、TIME、CMD | 关联终端、累计 CPU 时间、命令信息，CMD 的具体内容依格式 |

### 1.3 发送信号与终止进程

`kill` 用于发送信号，不是“删除程序文件”。不指定信号时通常发送 SIGTERM，进程可进行清理；SIGKILL 无法被捕获或忽略，但处于某些内核等待状态的进程也不保证立即消失。

以下 PID 1234 仅为示意，实际使用前先确认目标：

```bash
kill -TERM 1234
# 正常终止无效且确认影响后，才考虑强制终止。
kill -KILL 1234
# -9 是 SIGKILL 的常见写法。
kill -9 1234
```

按用户操作时先检查匹配范围：

```bash
pgrep -a -u sam
# 以下会影响该有效用户的所有匹配进程，包括会话和任务。
pkill -TERM -u sam
```

不要使用 `kill -9 $(ps -ef | grep 用户名)` 筛选并终止进程：命令替换会产生整段文本，再发生分词，不能直接当作 PID 列表。全角 `$（…）` 也不是 Shell 的命令替换语法。

## 2.Linux定时任务

### 2.1 用户与系统 crontab

| 类型 | 常见管理入口 | 格式 |
| --- | --- | --- |
| 用户任务 | `crontab -e` 编辑、`crontab -l` 查看 | 五个时间字段后直接接命令 |
| 系统任务 | `/etc/crontab`、支持此机制的 `/etc/cron.d/` | 五个时间字段后增加执行用户名，再接命令 |

用户任务通常用 `crontab` 管理，不直接编辑 spool 文件。存储位置依实现变化，例如 `/var/spool/cron` 或 `/var/spool/cron/crontabs`，不是所有任务都必须写入 `/etc/crontab`。

用户 crontab 示例：

```cron
SHELL=/bin/bash
PATH=/usr/bin:/bin
MAILTO=root

# 每 10 分钟记录一次时间，输出到当前用户可写的日志。
*/10 * * * * /usr/bin/date >> "$HOME/cron-time.log" 2>&1
```

`MAILTO` 指定输出邮件的接收者，是否发送成功还依赖本机邮件设施。以上注释独立成行，避免被当作命令的一部分。

系统 crontab 的对应示例，假设 sam 已存在：

```cron
*/10 * * * * sam /usr/bin/date >> /home/sam/cron-time.log 2>&1
```

实际家目录、目录权限和程序路径需核实。任务环境通常不同于交互式登录环境，不应假定相同的 PATH、别名和工作目录。

### 2.2 时间字段

| 顺序 | 字段 | 常见取值 |
| --- | --- | --- |
| 1 | 分钟 | 0—59 |
| 2 | 小时 | 0—23 |
| 3 | 月内日期 | 1—31 |
| 4 | 月份 | 1—12 |
| 5 | 星期 | 0—7，0／7 均为周日（此处按 Cronie 等常见实现） |

| 表达式 | 含义，不含后续命令 |
| --- | --- |
| `* * * * *` | 每分钟 |
| `0 8,12,16 * * *` | 每天 8、12、16 点整 |
| `0 5 * * 1-6` | 周一至周六 5 点整 |
| `*/10 * * * *` | 每小时的 0、10、20、30、40、50 分钟 |

使用 ASCII 的 `*`、`,`、`-`、`/`。步长在各自字段内计算，不是“上次任务执行完后再过 10 分钟”。在此类 cron 实现中，月内日期和星期均有限制时通常按“或”匹配，不能一律当作同时满足。

## 3.Linux相关日志

| 入口 | 用途与环境条件 |
| --- | --- |
| `/var/log/cron` | 一些发行版的 cron 日志；是否存在受 syslog 配置影响 |
| `/var/log/syslog` | 一些 Debian／Ubuntu 系统可能在这里记录 cron 等信息 |
| `/var/log/cups/` | CUPS 打印服务日志目录；需安装并启用相应服务及日志 |
| `journalctl` | 使用 systemd journal 的系统可从这里查询服务日志 |

```bash
# 服务名可能是 cron 或 crond，按实际系统选择。
journalctl -u cron --since "1 hour ago"
journalctl -u crond --since "1 hour ago"
```

先确认服务名及日志后端，再定位日志。没有某个文件不等于没有运行记录；任务输出、调度记录和认证日志也不是同一类证据。

## 4.安全加固

> **适用条件**：以下是策略说明和配置片段，不是适用于所有发行版的一键模板。认证配置受 PAM 模块、控制标记及顺序共同影响；修改前保留可用管理会话和恢复途径，修改后用新会话验证。本文不提供完整 PAM 认证栈。

### 4.1 口令失败锁定：历史方案与替代方案

#### 4.1.1 pam_tally2 旧版用法

**版本边界**：Linux-PAM 上游 1.4.0 已弃用并默认不再构建 pam_tally／pam_tally2，1.5.0 将其移除；发行版可能回移补丁或调整打包，仍应以目标系统实际模块和手册为准。旧环境具备模块时保留以下写法：

```pam
auth required pam_tally2.so onerr=fail deny=5 unlock_time=600 root_unlock_time=600
```

- 这是 PAM 片段，应根据该系统的完整认证流程安排位置，不能笼统要求“加在第一行”。
- `deny=5` 设置拒绝阈值，`unlock_time=600` 设置相应解锁等待时间；失败计数、成功重置及具体触发时点应对照该版本验证。
- `onerr=fail` 表示计数处理出错时返回失败。
- `root_unlock_time=600` **隐含对 root 也启用拒绝策略**，不能视作无条件安全的默认项。
- 成功认证后的计数重置涉及相应的 setcred／account 流程，孤立复制一行不能证明策略完整生效。

查看和重置旧计数器：

```bash
pam_tally2 -u sam
pam_tally2 -r -u sam
```

重置通常需要相应管理权限；这里只重置此模块的失败计数，不代表解除所有其他账户限制。

#### 4.1.2 pam_faillock 用法边界

在提供 pam_faillock 的系统上，应通过发行版支持的认证配置方式接入完整流程；某些系统使用 authselect 或 pam-auth-update 等工具管理文件，避免直接覆盖自动生成的认证栈。

仅在已正确接入模块、且版本支持该配置文件时，`/etc/security/faillock.conf` 可采用如下**参数示例**：

```ini
deny = 5
fail_interval = 900
unlock_time = 600
```

表示在 900 秒统计窗口内按阈值计数，满足锁定条件后按 600 秒解锁策略处理。单独创建文件不会自动启用认证锁定，也没有在此例中主动要求锁定 root。

```bash
faillock --user sam
faillock --user sam --reset
```

验证失败次数、成功登录后的计数变化、解锁时间及受影响的登录服务。pam_tally2 和 pam_faillock 的计数工具及数据不能直接混用。

### 4.2 密码复杂度

配置文件通常为 `/etc/security/pwquality.conf`；仅修改文件并不保证所有认证服务均执行质量检查，还需应用或 PAM 接入 libpwquality。无需把文件中所有注释行去掉，只启用需要的配置项。

```ini
minlen = 8
dcredit = -1
ucredit = -1
lcredit = -1
ocredit = -1
maxrepeat = 3
```

- 上面是参数教学示例，不是统一安全标准；四种 credit 均为负数时，要求相应类别至少各有 1 个字符，minlen 按真实字符长度计。
- **正 credit 表示该类别可获得的长度计分额度**，不是“允许出现的字符数量上限”；正数可能影响 minlen 的计算。
- `maxrepeat=3` 限制同一字符连续重复，因而不接受 `aaaa` 这类连续 4 个相同字符。
- 字典检查、对 root 的强制检查、模块参数及配置覆盖也影响最终结果。检查真实改密流程，而不是只检查文件内容。

### 4.3 密码有效期

`/etc/login.defs` 中的示例：

```text
PASS_MAX_DAYS 180
PASS_MIN_DAYS 0
PASS_WARN_AGE 15
```

分别表示最大使用天数、两次改密最小间隔和到期预警天数。具体默认值需查看系统配置；99999 是一个很大的天数，不应严格解释为永不过期。

这三项通常在**创建账户时**初始化老化信息；修改后不会自动改变已有账户，已有用户自行改密也不等于重新导入这组默认值。可按需要使用：

```bash
chage -l sam
# 修改已有账户的老化参数；先确认策略及目标。
chage -M 180 -m 0 -W 15 sam
```

参数名应写为 `PASS_MAX_DAYS`、`PASS_MIN_DAYS` 和 `PASS_WARN_AGE`。历史 `PASS_MIN_LEN` 也不能作为现代 PAM 密码复杂度策略的通用配置项；当前质量要求应按实际 PAM／libpwquality 实现设置。

### 4.4 账户清理与空口令检查

- 先核对账户用途、登录 Shell、服务依赖及文件归属，再决定禁用或删除。普通用户 UID 起点常由 `UID_MIN` 等配置决定，不能一律按“从 1000 起”识别无关账户。
- 系统账户也可能持有关键资源；删除方式及影响见 [06.Linux用户权限管理](./06.Linux用户权限管理.md)。
- 空口令验证字段、锁定标记和无法用于口令验证的字符串含义不同；锁定口令也不一定禁止密钥等其他登录方式。

具有读取权限时，可只输出空口令字段对应的用户名：

```bash
awk -F: 'length($2)==0 {print $1}' /etc/shadow
```

是否允许空口令登录仍取决于应用与 PAM 等策略；该检查也不覆盖所有远程身份源。

### 4.5 限制 su 到 root

在支持 Linux-PAM 的系统中，相关服务文件通常是 `/etc/pam.d/su`。下面是两条独立规则的片段，不是两种可随意互换的完整方案：

```pam
auth sufficient pam_rootok.so
auth required pam_wheel.so use_uid root_only group=wheel
```

- `pam_rootok.so` 可使真实 UID 为 0 的调用者按该控制规则通过。
- `pam_wheel.so` 配合 `root_only` 将组限制用于目标 UID 为 0 的切换；`use_uid` 检查调用进程的真实 UID 对应用户。
- wheel 组需按策略存在并维护；不是所有发行版都用这个组。
- 这些检查不替代其余口令认证规则。模块名与参数分别为 `pam_rootok.so`、`pam_wheel.so` 和 `use_uid`，注意拼写。

修改后分别验证 root、允许组成员及非成员的预期行为；还需检查其他 su 服务入口是否走相同规则。

### 4.6 限制 root 通过 SSH 登录

在有效的 sshd 配置中设置：

```sshconfig
PermitRootLogin no
```

语法检查与有效配置查看：

```bash
sshd -t
sshd -T
```

`sshd -t` 通过不代表远程认证测试通过；`sshd -T` 可查看有效配置，存在 Match 时需按目标连接条件配合 `-C` 检查。Include、匹配规则及启动参数都可能影响配置结果。

先确认普通管理账户能够登录并完成所需管理操作，再按实际服务名重新加载。服务可能叫 ssh 或 sshd；不要直接套用另一个发行版的服务名。

### 4.7 加固脚本与带空格文件名

以下写法执行**当前目录**中的脚本：

```bash
./Linux\ security.sh
# 等价的路径引用方式：
"./Linux security.sh"
```

反斜杠可转义空格；这两种写法仍要求脚本路径、执行权限及解释器条件满足。先阅读脚本、确认目标环境与改动范围，再在实验环境验证；“一键”不代表可跳过策略核查和结果验证。
