## 1.网站协议抓包：先看流量经过哪里

抓包可以先想成“在数据经过的路上观察”。Burp 常用的方式是让应用主动把请求交给代理；Wireshark 则是在选定的网络接口上观察流量。两者能看到什么，取决于观察位置、协议与加密条件。

### 1.1 Burp 与浏览器代理

Burp Suite 常简称 BP，适合查看、拦截和修改 Web 请求与响应，也能处理 WebSocket 消息；它不是任意网络协议都能直接读懂的通用网卡抓包器。

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755593021499-d868de6e-5ffa-4497-8b01-cc5c922152df.png)

典型路径：

```text
浏览器 → 本机 Burp 代理监听端口 → 网站
浏览器 ← 本机 Burp 代理监听端口 ← 网站
```

1. 先检查 Burp 的 Proxy 监听配置。`127.0.0.1:8080` 是常见本地设置，不是不能修改的固定值。
2. Burp 内置浏览器已配置好相关代理，入门时可先用它确认链路。
3. 外部浏览器可通过浏览器设置或原笔记提到的 SwitchyOmega 等代理配置工具，把需要观察的流量送到 Burp。
4. 在 HTTP history 查看是否有记录；Intercept 打开时，请求可能停在 Burp 等待放行，浏览器一直转圈不一定是网络故障。

系统代理只对遵循这套配置的应用有效。微信小程序或其他桌面客户端是否经过代理，要实际观察请求记录；不能从“已经改了 Windows 代理”推出所有协议都被捕获。

### 1.2 HTTPS 与证书

HTTP 明文经过代理时通常可直接查看；HTTPS 要让 Burp 参与 TLS 连接并查看明文，还需要客户端信任相应 CA，且应用没有其他阻止条件。

可以把 CA 信任理解成“客户端认可由这个检查站签发的站点证书”。**装过证书不等于一定能抓到所有 HTTPS**，代理链路、信任位置和应用自身校验都要满足。

- 外部浏览器按官方步骤导入 Burp 导出的 CA，建议使用专门的实验浏览器或测试配置。
- 浏览器和操作系统可能使用不同证书库，安装位置需按实际实现确认。
- 把文件后缀改成 `.cer` 只是在改名字，不会自动完成 PEM／DER 格式转换。
- 工具中的可读 HTTP 内容，是在相应解密或代理条件下展示的结果，不代表线上 HTTPS 本来就是明文。

### 1.3 手机与模拟器

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755602071244-682b67cc-e301-4506-8e78-ab64f8c53db2.png)

模拟器中的 `127.0.0.1` 通常指模拟器自己，不是运行 Burp 的电脑。Android Studio Emulator 通常可用 `10.0.2.2` 访问宿主机回环接口；其他模拟器、虚拟机及真机要按实际网络选取地址。

先配置可达的代理地址，并确保 Burp 监听在对应接口、端口未被阻断，再处理证书。不要一上来就把“抓不到”归结为证书问题。

原流程“共享目录放证书 → 设置中的安全／凭据入口 → 从存储安装”可作为旧界面参考，但要留意：

- 以系统相应安装入口支持的格式导入，入口名称随系统和厂商变化；原文的 sdk 卡应理解为存储／SD 卡入口。
- 在 Android 7.0 及后续支持该机制的系统上，默认信任行为与应用的 **targetSdkVersion** 有关。目标 API 23 及以下应用默认也信任用户 CA；目标 API 24 及以上默认不再因此自动信任用户 CA，应用可另行配置。
- 应用不必是 WebView 才使用 HTTP。原生网络库同样可能使用 HTTP(S)，但是否遵循代理、是否有证书固定或自定义 TLS 校验，要分别判断。

### 1.4 抓不到时的排查顺序

| 现象 | 先查什么 |
| --- | --- |
| Burp 完全没有记录 | 应用是否走代理、地址能否到达、监听是否正确、是否设置了绕过规则 |
| HTTP 有记录，HTTPS 报证书错误 | CA 装在哪个信任库、应用是否接受该 CA、目标域名与证书校验是否匹配 |
| 浏览器能抓，某个应用抓不到 | 应用代理行为、网络库及自定义认证；不要直接推断为“工具失效” |
| 请求一直不返回 | Intercept 是否等待放行、上游连接和代理配置是否正常 |
| 部分功能缺少数据 | 可能使用 WebSocket、QUIC 或其他通道，也可能选错过滤条件；需要结合网卡流量观察 |

更详细的 Burp 操作接着看 [11.BurpSuite详解](./11.BurpSuite详解.md)。

## 2.网卡抓包与其他工具

“全局抓包”是原课程的通俗叫法，更准确地说，是在指定接口和权限条件下观察它能收到的流量；不能理解为自动看到整个局域网每台机器的所有通信。

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755604156782-5c28e5ec-e102-4560-9271-8db05221ffee.png)

### 2.1 工具各自负责什么

| 工具 | 主要用途 | 注意点 |
| --- | --- | --- |
| Wireshark | 捕获并分析网络接口上的报文 | 选对网卡、驱动及权限；有 TLS 密文不代表已经能解密 |
| 科来相关分析工具 | 按相应产品能力做流量分析 | 名称、菜单、功能与具体版本对应 |
| WPE 等旧工具 | 某些环境下按进程观察或操作通信 | 保留历史学习资料，兼容性和协议支持不能推广到所有系统 |
| Proxifier | 按规则让连接经过代理 | 主要是流量转发工具，不能直接等同于协议分析或解密工具 |

Wireshark 常见的第一步是选网卡：连 Wi-Fi 时、使用 VPN 时、观察回环或虚拟机流量时，正确的接口可能不同。

### 2.2 过滤与加密边界

```text
捕获过滤器示例：tcp port 80
显示过滤器示例：tcp.port == 80
```

前者在捕获阶段筛选，后者筛选已经捕获的报文，语法不能混用；这两个例子也只针对指定 TCP 端口，不代表所有 HTTP 都在 80 端口。

“看得到包”和“看得懂内容”是两件事：网卡上能看到 HTTPS 对应的连接信息，内容仍可能是密文。要进一步分析明文，需满足受支持的会话密钥或代理解密条件，不是安装 Wireshark 后就自动具备。
