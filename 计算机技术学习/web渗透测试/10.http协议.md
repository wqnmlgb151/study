## 1.HTTP：浏览器和服务器怎样说话

HTTP 是应用层协议，常按“发请求、收响应”的方式交互。可以先把报文理解成一张信息单：先说明要做什么，再附上必要的描述和数据。

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755679136616-e995e855-c064-4dd5-9dbc-aa0a3ae52669.png)

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755610261072-e6c478a5-8022-4d50-a048-3c70674a50f2.png)

### 1.1 无状态，不等于每次都断线

**无状态**指协议本身不要求服务器记住前一次请求与当前请求的关系，不表示网站不能保持登录。应用可通过 Cookie、会话标识或令牌把多次请求联系起来。

**连接复用**是另一个问题：HTTP/1.1 默认支持持久连接，一条连接可承载多次请求。早期 HTTP 常用短连接，仍需建立底层 TCP 连接；原笔记的“无连接”不能理解为不建立连接，也不能作为所有 HTTP 版本的共同特征。

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755657625579-ebfc3838-6f89-47e8-a4ee-d88e19e4910d.png)

### 1.2 看报文前，先认清版本

| 版本 | 抓包时需要知道的区别 |
| --- | --- |
| HTTP/1.0、HTTP/1.1 | 通常运行在 TCP 上；本篇后面的请求行、状态行例子按 HTTP/1.1 文本形式展示 |
| HTTP/2 | 在 TCP 上使用二进制帧与多路复用；工具可能整理成便于阅读的头部视图 |
| HTTP/3 | 把 HTTP 映射到 QUIC，通常使用 UDP；不能套用“所有 HTTP 都基于 TCP” |

HTTPS 提供受 TLS 等机制保护的 HTTP 通信。它保护传输链路，不代表应用自动没有注入、越权或其他逻辑问题。具体加密知识见 [12.数据传输与加密算法](./12.数据传输与加密算法.md)。

## 2.HTTP 请求：客户端想做什么

[常见的请求头 响应头.docx](https://www.yuque.com/attachments/yuque/0/2025/docx/59258918/1755670392632-8cad6d77-4bc1-4196-af74-f649c38cf4d4.docx)

### 2.1 先看一个最小示例

这是教学用的 HTTP/1.1 文本视图，HTTPS 在代理中被正确解密后也可以这样阅读：

```http
POST /login HTTP/1.1
Host: lab.example.test
Content-Type: application/x-www-form-urlencoded
Content-Length: 26

username=lab&password=test
```

从上往下看：

1. **请求行**：方法、请求目标、版本。这里的请求目标是 `/login`；常见形式是路径和查询字符串，不必总写完整 URL。
2. **请求头**：如 Host、Content-Type 等，用来描述请求及其数据。
3. **空行**：分开头部与消息体。
4. **消息体**：此例是表单内容；Content-Length 按内容字节数计算，这里为 26。

线上 HTTP/1.1 使用规定的行结束格式，示例为方便阅读省略字节层面的展示。也有使用其他消息定界方式或不带消息体的请求，不能把这一个例子当作全部报文格式。

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755673135865-bfdd1ba0-a1f4-4580-a56a-02781d46ba03.png)

### 2.2 常见方法

原笔记列出了八个基础方法，但方法是可扩展的，不能理解为“总共只有八种”。大小写及拼写也应准确，例如 **OPTIONS**，不是 Option。

| 方法 | 可以怎样理解 |
| --- | --- |
| GET | 获取目标资源的内容，例如网页、数据或文件 |
| POST | 把内容交给目标资源按自身规则处理，例如提交表单、创建资源或触发动作 |
| HEAD | 与 GET 类似，但响应不包含消息内容；仍有状态和头部 |
| PUT | 按请求内容创建或替换目标资源，语义上是幂等的 |
| DELETE | 请求删除目标资源，但不保证底层文件会被物理擦除 |
| OPTIONS | 询问目标支持哪些通信选项，例如可用方法；不等于认证授权检查 |
| TRACE | 请求应用层回环，用来观察请求在路径中的变化；服务可能禁用 |
| CONNECT | 请求建立隧道，常用于代理 |
| PATCH | 按补丁描述做部分修改，是对基础方法的扩展；不保证天然幂等 |

**幂等**看的是重复请求的预期服务端效果，不要求每次状态码和响应内容都一样。实际接口若违反方法语义，还需要根据实现分析。

### 2.3 GET 与 POST：参数放哪，不决定安全高低

GET 常把筛选条件放在查询字符串中，例如 `/search?q=linux`；POST 常把提交数据放在请求体里，也完全可以同时带查询字符串。

**POST 不是 GET 的“加密版”。** HTTP 明文传输时，两者的数据都可能被路径上的观察者读取；传输保护依赖 HTTPS。HTTPS 下，URL 路径和查询在正常 TLS 链路中也受保护，但仍可能进入浏览器历史、应用日志或其他记录，需结合场景分析。

URL、请求头和请求体的长度限制来自具体浏览器、代理和服务器等，不存在一个通用于所有系统的“GET 最大长度”。GET 消息体的含义和支持也不能按 POST 想当然套用。

Burp 可按工具支持转换请求方法，但转换后需要检查参数、Content-Type 及服务器实际处理结果。协议版本也不是随手改一段文字就能任意切换的；必须与工具和对端的支持情况匹配。

### 2.4 常见头部：能提供线索，也能被误解

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755678368113-a5c6262a-9415-48a9-8d9a-ce8c0a0d9eb0.png)

| 字段 | 看什么 |
| --- | --- |
| Host | HTTP/1.1 中的目标主机／端口信息；要结合请求目标及代理行为分析 |
| Content-Type | 内容格式，不是内容本身一定安全的证明 |
| Content-Length | 内容长度；按字节而非显示字符数理解 |
| Cookie | 客户端按条件发送的 Cookie，其中可能含会话标识，也可能只是偏好设置 |
| Referer | 来源信息，可能因策略省略；拼写沿用协议字段的历史写法 |
| User-Agent | 客户端自报的产品信息，可修改，不能单独证明使用者或工具身份 |

Cookie 并非全部都用于登录，Referer 也不是身份凭证；两者一起出现不等于自动组成“双重身份认证”。获得一个 Cookie 值是否能复用会话，还取决于其用途、有效性、服务端状态和相关绑定条件。

Cookie 的下发通常看响应里的 **Set-Cookie**；后续请求才可能带上 **Cookie**。登录态与服务端授权的区别可继续对照 [17.身份验证原理](./17.身份验证原理.md)。

## 3.HTTP 响应：服务器怎样回答

### 3.1 状态、头部与消息体

与上面教学请求对应，一个示意响应可以写成：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 11

{"ok":true}
```

第一行是 HTTP/1.1 的**状态行**，含版本、状态码和原因短语；随后是头部、空行及消息体。上例消息体为 11 个字节，展示用的尾部换行不计入内容。

HTTP/2、HTTP/3 不直接在网络上传输同样的文本状态行；工具的可读视图不能反推线上就是这些文本字节。

在 Burp 里可以用相应拦截规则或请求的上下文菜单截住响应。具体菜单按版本核对；只在 history 里看到响应，与正在拦截并等待转发，是不同状态。

![](https://cdn.nlark.com/yuque/0/2025/png/59258918/1755682465287-10f51c77-219b-4aa3-be4e-35ad69bc0655.png)

### 3.2 状态码怎么读

先看类别，再看具体含义：

| 类别 | 大致含义 | 常见例子 |
| --- | --- | --- |
| 1xx | 处理过程中的提示 | 100 Continue |
| 2xx | 本次请求按相应语义处理成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向或其他后续处理信息 | 302 Found、304 Not Modified；304 不是跳转页面 |
| 4xx | 请求侧相关的问题 | 400、401、403、404，具体原因仍需上下文 |
| 5xx | 服务端处理失败 | 500、502、503 |

200 只说明 HTTP 层面的相应结果，不保证业务登录成功；有些接口会在 200 的 JSON 里返回业务错误。HEAD 响应及 204 等情形也不能照普通 200 响应推断一定有消息体。

### 3.3 从响应找线索，最后仍看服务端事实

`Server` 等响应头可以提供服务器或中间件线索，但可能被隐藏、修改，也可能来自反向代理；不能仅靠一个字段确认技术栈和版本。

原笔记提到“把失败响应改成成功”。这个实验值得保留，不过要继续分清结果：

- 只让页面显示“成功”，可能只是改了客户端看到的内容。
- 如果随后访问受保护接口仍被拒绝，就没有证明服务端身份验证被绕过。
- 如果未满足应有条件，却实际获得受保护数据或完成敏感动作，才进一步检查服务端认证、授权或业务校验的问题。

因此，应保留原始请求、服务端响应和后续操作结果；修改响应可以帮助定位客户端信任问题，不能自动把所有“页面变成功”都归类为已成立的登录绕过。
